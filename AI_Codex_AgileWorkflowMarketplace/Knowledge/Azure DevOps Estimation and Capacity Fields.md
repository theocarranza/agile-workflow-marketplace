# Azure DevOps Estimation and Capacity Fields

How Azure DevOps splits estimation across two tiers, which fields feed which reports, and why Tasks generated by this plugin currently register as empty on both the capacity view and the sprint burndown.

## What this document is

A reference for anyone changing how the plugin writes Tasks into Azure DevOps. It records what the official documentation says about estimation and capacity, then states a concrete gap found in the breakdown skill and the options for closing it. Read it before adding any estimate-bearing field to work-item creation.

## Background

Azure DevOps keeps two independent estimation systems, and they never talk to each other.

The **backlog tier** carries a relative size on each Story. It is a judgment about how big something feels next to other work, not a measure of time. This tier drives **velocity** — the amount of size a team completes per sprint, used to forecast how much will fit in the next one.

The **task tier** carries absolute hours on each child Task. This tier drives sprint capacity and the **burndown chart** — the line showing how much work is left as the sprint runs down.

```
Story  ──  relative size (points)
  │            └─→ velocity, forecasting
  │
  └─ Task ──  absolute hours
                 └─→ capacity bars, burndown
```

Which field holds the relative size depends on the **process** — the work-item template a project was created from. Azure DevOps ships three.

| Field | Reference name | Process | Applies to |
| --- | --- | --- | --- |
| Story Points | `Microsoft.VSTS.Scheduling.StoryPoints` | Agile | User Story, Bug |
| Effort | `Microsoft.VSTS.Scheduling.Effort` | Scrum | Product Backlog Item, Bug |
| Size | `Microsoft.VSTS.Scheduling.Size` | CMMI | Requirement |

All three map to the same `Effort` slot in the **process configuration** — the file that tells Azure DevOps which field means what. That mapping is why any of the three can feed velocity and appear in the burndown chart's "sum of" selector, even though the field names differ.

The task tier uses three numeric fields plus one classifier.

| Field | Reference name | Behaviour |
| --- | --- | --- |
| Original Estimate | `Microsoft.VSTS.Scheduling.OriginalEstimate` | Set once, rarely changed afterwards |
| Remaining Work | `Microsoft.VSTS.Scheduling.RemainingWork` | Updated as work progresses; drives capacity and burndown |
| Completed Work | `Microsoft.VSTS.Scheduling.CompletedWork` | Effort already spent |
| Activity | `Microsoft.VSTS.Common.Activity` | Type of work, such as Development or Testing; named `Discipline` in CMMI |

One process difference matters when writing code against these fields. **Scrum ships only Remaining Work.** Agile and CMMI ship all three. Any workflow that depends on Original Estimate breaks silently on a Scrum project unless the process has been customised.

## Problems and evidence

### The breakdown skill writes no estimates at all

The skill that generates Tasks from a Story, `generate-breakdown-work-items`, sets no estimation field on any Task it creates. A search across all six files in the skill for the scheduling field names, and for the words `estimate` and `hours`, returns nothing.

- Task creation passes only a title, a description, and a description format — see `agile-workflow/skills/generate-breakdown-work-items/references/atomic-tasks.md:87-102`.
- The only field update afterwards targets the assignee and the state, and only on the final Breakdown Task.
- The shared Azure instructions at `agile-workflow/references/azure-mechanics.md:32` mention setting points at Story creation, but say nothing about Task-level fields.

### Generated Tasks are invisible to capacity and burndown

Capacity bars and the sprint burndown both work by summing Remaining Work across the Tasks in an iteration. With that field left empty, a Story broken down by this skill lands on the sprint board contributing nothing to either view.

- The Tasks exist and are correctly parented, so the hierarchy looks healthy while the sprint tooling reports an empty sprint.
- Velocity is unaffected, because it reads the Story's relative size, which the plugin already sets.

### Work type is never classified

Teams that divide capacity by activity — allocating separate hours to development and to testing — depend on the Activity field. Every generated Task leaves it empty, so all of them fall into a single unallocated bucket regardless of what the Task actually does.

### Iteration assignment is unstated

No instruction sets `System.IterationPath` on generated Tasks, so they inherit whatever Azure DevOps assigns by default rather than following the parent Story explicitly. Whether that is deliberate is not recorded anywhere in the skill.

## Core idea

The Story tier is already wired correctly in this plugin, and the Task tier is not. The quality gate at `agile-workflow/skills/validate-artifact/references/validation-checks.md:57` fails any artifact whose points field is zero or unset, and the sizing skill reads the same field at `agile-workflow/skills/split-story/SKILL.md:57`. Nothing equivalent exists one level down.

Closing the gap means writing Remaining Work, and probably Activity, at Task creation.

## Out of scope

This note does not cover pipelines, dashboards, or the relative-sizing rules the team uses to arrive at a number. It describes which field to write, not what value belongs in it.

## Delivery plan

Any change follows the existing persist step rather than adding a new phase.

1. Decide where the hour value comes from — see the open question below.
2. Extend the Azure persist step in `agile-workflow/skills/generate-breakdown-work-items/references/atomic-tasks.md` to set Remaining Work on each created Task.
3. Set Activity when the host team plans capacity by activity type, leaving it unset otherwise.
4. Add both fields to the existing read-back assertion, which already stops the run when a created Task fails verification.
5. Guard the Original Estimate path behind a process check, since Scrum projects do not have that field.

## Decisions to record

**Superseded 2026-07-28.** This note originally recorded that a generator must not invent hour values, and that any figure had to come from a person. That was decided before the feature had a shape. The implemented design replaces it:

Hours are **derived** from the Story's points and split across its Tasks, so there is no invention and nothing for a person to approve item by item. They are written automatically, and **every figure set or changed is reported** (old → new) — nothing asked permission, so nothing moves silently. Recomputes are automatic for the same reason: a Task list that changed but kept its old hours is worse than one with no hours, because the burndown then charts a plan nobody is following.

The judgement that still needs a person is **whether the work fits**. When the derived hours exceed the assignee's remaining capacity in the active sprint, the run stops and asks — split, reschedule, reassign, or reduce scope. Hours are never scaled down to fit.

**Process capability must be checked before writing Original Estimate.** Writing it unconditionally fails or silently drops the value on Scrum projects.

## Open questions

**Where should the hour value come from?** The recommendation is to collect it during the Task selection step the skill already runs, since that step is an existing interaction point and the person selecting Tasks is the one who can size them. The alternative — writing an empty Remaining Work and flagging it in the run summary as needing team input before the sprint starts — is cheaper to build but relies on someone acting on the flag. Prefer the first unless the selection step is already too long.

**Is default iteration inheritance intentional?** The recommendation is to set the iteration path explicitly from the parent Story, so Task placement does not depend on host defaults that vary by project.
